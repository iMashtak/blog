# Шаблонизация конфигурационных файлов

Обычно для шаблонизации конфигурации используется какой-нибудь шаблонизатор: Jinja2, Mustache. В целом, решение логичное, но оно имеет критический недостаток: парсить шаблон конфигурации нужно именно в языке шаблонизатора, а не в языке конфигурационного файла.

Попробую привести пример:

```yaml
{% if value %}
property: {{ value }}
{% endif %}
```

Это шаблонизированный YAML. Человеку очевидно, что результатом рендеринга будет YAML. Но данный шаблон невозможно анализировать как YAML-файл, так как реальный синтаксис - Jinja2.

## Решение

Можно подумать в сторону того, чтобы делать шаблон в синтаксисе исходного языка. Фактически, конструкции шаблонов необходимо реализовать так, чтобы они не требовали дополнительной грамматики и YAML-шаблон парсился бы обычным YAML-парсером.

Так, подстановку переменной можно обозначить следующим образом:

```yaml
property: ${value}
```

Условный оператор:

```yaml
$ if value:
  property: ${value}
```

Данный шаблон будет отрендерен в

```yaml
# value = true
property: true
```

То есть `if`-конструкция при рендеринге подставляет свои child-элементы вместо себя.

Да, в данной нотации вводится ограничение на то, что ключи конфигурации не должны начинаться на символ `$`, так как он служит указателем на то, что в этом ключе будет записана управляющая конструкция.

Цикл:

```yaml
$ for item in items:
  - value: ${item}
```

Точно так же цикл сгенерирует необходимое количество элементов списка и подставит этот список на своё место. Получится:

```yaml
- value: item1
- value: item2
```

Не очень очевидно, как реализовать конструкцию `let`, то есть присваивание значения, действующего в рамках шаблона.

```yaml
$ let x: ${items.map(x -> x.toLower())}
```

В момент рендеринга данный ключ необходимо просто исключить из результирующего YAML. Также необходимо разобраться с областями видимости:

```yaml
$ let modulesLower: ${modules.map(x -> x.toLower())} # видно во всём документе
logging:
  level:
    $ let defaultLogLevel: info # видно только в контексте logging.level
    root: ${defaultLogLevel}
    modules:
      $ for module in modulesLower: # module видно только в контексте цикла for
        ${module}: ${defaultLogLevel}
```

Проблема возникнет в случае, когда `let`-конструкция будет единственным child-ом некоторого ключа:

```yaml
root:
  $ let x: ${items.map(x -> x.toLower())}
```

В целом, в такой конструкции нет смысла, так как переменная `x` всё равно не будет нигде использоваться. Всё же, это корректный YAML и становится непонятно - после рендера `root` должен стать `null` или пустым объектом `{}`.

## Что это даёт?

Пусть шаблон будет называться конфигом, а подстановочные параметры будут называться энвами. Имея описанный выше шаблон становится возможным вывести типы значений энвов с помощью JSON Schema конфигурации.

Зачем вообще нужны типы энвов? Фактически, энвы являются тем, с чем администратор системы будет взаимодействовать. Если администратор ошибётся на этапе записи значений переменных, то эта ошибка выявится только на этапе рендера конфига, что может произойти непосредственно при деплое системы. Выглядит крайне неудобно и ненадёжно. В то же время, если бы у администратора были бы типы энвов (выраженные в виде той же JSON Schema), то вероятность ошибок существенно снизилась бы. Сгенерировать такую схему не составит труда в случае использования предложенной выше шаблонизации.

Также:

- такой шаблон намного более читаемый, чем наслоение той же Jinja2 на YAML;
- с ним будет корректно работать подсветка синтаксиса и автодополнение;
- значения будут подставляться не как текст, а как типизированные YAML-сущности. Возьмём такой пример:
    ```yaml
    # env.yaml
    myvar: "true"
    mybool: true
    ```
    ```yaml
    # config.yaml
    enabled: ${mybool}
    text_param: ${myvar}
    ```
    Так как предложенная шаблонизация работает в терминах YAML-сущностей, то для `enabled` будет подставлено логическое значение из переменной `mybool`, а в `text_param` уже строковое значение `myvar`. Дополнительно следить за экранированием подстановочных параметров не нужно.
- разбиение конфигурации на файлы становится тривиальным - процедура импорта будет парсить импортируемый файл как YAML и подставлять его значение напрямую в качестве child-элемента в корневой YAML-конфиг. Вот так это может выглядеть:
    ```yaml
    # config.yaml
    p1: v1
    $ import: part.yaml
    ```
    ```yaml
    # part.yaml
    p2: v2
    ```
    ```yaml
    # rendered.yaml
    p1: v1
    p2: v2
    ```

## Не YAML-ом единым

Данный подход работает для любых JSON-подобных форматов конфигурации.

JSON:

```json
{
    "p1": "v1",
    "$ import": "part.yaml"
}
```

TOML (требуется экранирование символа `$`):

```toml
p1 = "v1"
"$ import" = "part.yaml"
```

Вообще, подобная техника используется для XML-подобного формата шаблонов Vue. Там используются `v-if` и `v-for` в качестве атрибутов XML-тега, позволяя таким образом включать конкретный тег в разметку (или нет), или генерировать множество child-элементов родительского тега.

```vue
<template>
    <p v-if="seen">Now you see me</p>
    <li v-for="item in items">
        {{ item.message }}
    </li>
</template>
```

Почему такой подход не переносится на JSON-подобные форматы - я так и не понял, поэтому эта заметка и существует. Также без ответа останется вопрос, почему я до сих пор не реализовал эту идею в виде какой-нибудь библиотеки.
