# AI Gateways

Хотелось бы разобраться, что входит в понятие AI Gateway, какая функциональность может или должна ими поддерживаться.

## Фичи

Сводное дерево фич:

- Поддержка протокола общения с LLM-провайдерами
    - HTTP/SSE
    - WebSockets
    - gRPC Streaming
- Идентификация пользователей
    - Интеграция по OIDC
- Поддержка различных API LLM
- Трекинг стоимости обслуживания пользовательских запросов к LLM
    - Лимитирование потребления токенов пользователем по временным промежуткам
    - Отслеживание стоимости взаимодействия с LLM
- Валидация запросов и ответов (guardrails)
    - Фильтрация неподходящих запросов (по произвольным критериям)
    - Маскирование информации
    - Распознавание попыток jailbreak-ов
- Кэширование ответов на запросы
    - Обычное кэширование
    - Семантическое кэширование
- Роутинг и балансировка нагрузки между моделями
    - Возможность выставления нескольких моделей за шлюзом
    - Автоматическое перенаправление запроса на менее загруженную в данный момент модель
    - Роутинг на наиболее подходящую модель в зависимости от поставленной в запросе задачи
- Observability
    - Панель обзора статистики использования LLM
    - Панель обзора сработок валидации запросов и ответов
- Трансформация запросов
    - Декорирование или шаблонизация промптов
    - Использование RAG
- Работа с нетекстовыми данными
    - Передача изображений как URL
    - Загрузка пользовательских изображений во внутренний CDN
    - Распознавание стеганографии
    - Кодировка изображений в текст
    - Передача аудио-данных
    - Конвертация документов в текст
- Поддержка протоколов взаимодействия AI-агентов друг с другом и с внешним миром
    - MCP
    - A2A

### Поддержка протокола общения с LLM-провайдером

Речь идёт о транспорте для работы с LLM - протоколах HTTP и SSE. Большинство моделей работают именно по SSE-протоколу, поэтому это скорее базовая необходимая функциональность.

Однако к LLM могут обращаться не только живые пользователи, но и разнообразные сервисы внутри инфраструктуры компании. Такие сервисы могут иметь дополнительные требования к тому, по какому протоколу общаться с LLM. В целом, такими протоколами могут быть стриминговые протоколы, например, WebSockets и gRPC Streaming. Преобразование протокола на шлюзе может быть важной функциональностью, востребованной в рамках организации.

Работа с протяжёнными во времени запросами (а именно такие запросы получаются ввиду длительного стриминга ответа от LLM) приводит к необходимости поддерживать отмену обработки запроса. То есть пользователь в любой момент может прервать соединение с шлюзом (путём закрытия вкладки браузера), и тот должен обработать это событие. Например, некоторые провайдеры не тарифицируют неполученные токены в ходе генерации ответа, поэтому имеет смысл прервать соединение и между шлюзом и LLM API с целью не тратить лишние токены.

### Идентификация пользователей

Для выполнения доступа к LLM API необходимо каким-либо образом авторизоваться в системе LLM-провайдера. Разные провайдеры используют собственные механизмы, но шлюз может абстрагировать это разнообразие подходов путём, например, авторизации пользователя по OIDC в Identity Provider-е организации и получить из него соответствующий API Key для доступа к конкретной LLM.

### Поддержка различных API LLM

Речь идёт, конечно же, про API провайдеров тех или иных LLM. Разные провайдеры предоставляют разные API, которые, помимо самого контента сообщения пользователя, содержат настроечные параметры. Например, таким параметром может быть настройка кэширования промпта на уровне модели. Включённое кэширование снизит стоимость использования LLM.

### Трекинг стоимости обслуживания пользовательских запросов к LLM

Трекинг стоимости обслуживания подразумевает необходимость считать количество использованных токенов в различных контекстах:

- в разрезе пользователя или группы пользователей (здесь понадобится идентификация пользователей)
- в разрезе временного промежутка (сколько токенов было потрачено за час, за месяц и т.п.)
- в разрезе используемой модели или провайдера

На полученное количество расходуемых токенов устанавливаются лимиты, например, сколько максимум может быть потраченных пользователем токенов в месяц на взаимодействие с конкретной моделью.

Эти лимиты критически важны для контроля использования LLM сотрудниками организации и планирования денежных затрат. Вообще, можно поставить в качестве лимитов не сырое количество токенов (которое довольно сложно оценить), а конкретное количество денег, которые эти токены стоят.

Токены бывают разных типов: входные токены из промпта, сгенерированные моделью токены, записанные в кэш токены, прочитанные из кэша токены. Каждый из видов токенов тарифицируется отдельно, отсюда критически важно правильно рассчитывать общую стоимость взаимодействия с LLM.

### Валидация запросов и ответов (guardrails)

Guardrails - общепринятый термин для валидации LLM-специфичных запросов. В целом, есть всего два варианта, как поступить с данными в запросе/ответе к/от LLM: либо отклонить (фильтрация), либо заменить некоторый контент другим (маскирование).

Некоторые системы реализуют десятки guardrails-ов на основе классических алгоритмов (распознавание информации по регулярным выражениям, например), либо с использованием моделей машинного обучения (не обязательно LLM).

При анализе трафика встаёт довольно необычная проблема при обработке ответа от LLM: так как ответ предоставляется в виде стрима, то невозможно сразу проанализировать весь ответ на предмет наличия признаков фильтрации или маскирования. Если анализировать каждый чанк ответа независимо, то может произойти так, что необходимая к маскированию информация окажется в двух последовательно идущих чанках, и тем самым guardrails маскирования не сможет детектировать данный факт. Ещё хуже ситуация, когда часть информации передаётся в начале ответа (сама по себе не являясь чувствительной), а другая часть, дополняющая предыдущую и делающая эту информацию в совокупности чувствительной, передаётся позже, в конце ответа. В обоих случаях необходимо анализировать не чанки независимо, а буферизировать ответ с начала и до конца и при добавлении каждого нового чанка анализировать целиком получившуюся конструкцию.

Отдельно стоит задача защиты от jailbreak-ов - методов обхода правил работы LLM и исполнения "небезопасных" действий. Безопасность тех или иных действий регулируется и понимается конкретным провайдером или может быть установлена на AI-агенте или шлюзе непосредственно. Так, например, AI-агент может быть настроен на предоставление только информации по конкретной теме (AI-чат/поиск на сайте организации). Пользователь же вводит запрос, совершенно не относящийся к деятельности организации, и, если нет механизмов защиты от этого, получает бесплатный (для пользователя, не для организации) сервис общения с какой-нибудь платной моделью. И это только самый безобидный сценарий jailbreak.

### Кэширование ответов на запросы

Кэширование можно разделить на два вида: обычное и [семантическое](https://docs.getbifrost.ai/features/semantic-caching). Под обычным кэшированием подразумевается создание на шлюзе прямого соответствия между запросом и ответом. Однако это не очень эффективно в случае общения пользователей с LLM: каждый пользователь может написать "добрый день" модели по-своему, хотя один и тот же возвращаемый ответ удовлетворит каждого. Поэтому лучшим решением будет использовать векторную базу данных с возможностью поиска по ней для установления степени схожести входного запроса предыдущим. Такой вид кэширования и называется семантическим, так как использует смысл входного запроса, а не его форму.

### Роутинг и балансировка нагрузки между моделями

Довольно очевидным решением для шлюза будет возможность помещать "за ним" несколько различных моделей, обеспечивая тем самым единую точку доступа к AI-ресурсам организации.

Если некоторые модели развёрнуты внутри периметра организации, то появляется возможность использовать данные об их загруженности для автоматической балансировки нагрузки между ними - автоматически выбирать наименее загруженную модель для выполнения запроса пользователя.

Другой интересной функциональностью может являться автоматический выбор наилучшей модели для решения задачи. Так, на шлюзе можно проанализировать, какую именно задачу пользователь поставил в своём промпте перед моделью, и выбрать наилучшего кодера, наилучший поисковик, либо вообще наиболее дешёвую модель для исполнения этого запроса.

### Observability

Многие AI Gateway-и предоставляют собственные UI-панели управления собой. Это включает в себя средства как изменения параметров шлюза, так и мониторинга различных его свойств.

Так, ранее говорилось о трекинге взаимодействия с LLM, но должно же существовать место, где можно выставлять те самые лимиты на использование токенов (или их денежного эквивалента). Также должно быть возможно посмотреть по конкретному пользователю, сколько он использовал свой лимит. Возможно, эта функциональность не относится непосредственно к шлюзу - всё-таки это должна быть отдельная система мониторинга, но шлюз должен как минимум откидывать статистику во внешнее хранилище.

Также необходимо иметь возможность просмотреть логи системы, особенно сработки guardrails-ов. Резко возросший показатель количества сработок может сигнализировать на начало атаки на организацию.

Не обязательно реализовывать все эти механизмы в виде UI-панели, но необходимо иметь интеграции с системами сбора логов и мониторинга, в том числе AI-специфичных метрик.

### Трансформация запросов

Трансформация запросов обсуждалась и ранее в разделе про guardrails - там использовалось маскирование. Но здесь речь пойдёт о другом - об обогащении промптов, добавлении дополнительного контекста.

Всего можно выделить два подхода: детерминированный (декорирование и шаблонизация) и семантический ([RAG](https://habr.com/ru/articles/779526/)). В первом случае к пользовательскому промпту добавляется статическая информация в виде некоторых дополнительных строк, влияющих на ответ LLM. Во втором случае используется подход, при котором в запрос к LLM добавляется информация, извлечённая из специальной базы данных. Этой базой может быть база знаний организации или документация по продукту. Такой подход и называется RAG - Retrieval Augmented Generation. Саму базу данных (точнее, доступ к ней) можно хранить на шлюзе, тем самым позволяя делать тематические шлюзы.

### Работа с нетекстовыми данными

Основные варианты обрабатываемых LLM нетекстовых данных - изображения и аудио.

Отдельно рассмотрим случай изображений. В целом, в запросе к модели можно указать тип сообщения `image` и передать URL до желаемой к обработке картинке. Однако для обработки картинки она должна быть доступна модели. Поэтому удобной функциональностью шлюза была бы публикация картинки в внутреннюю CDN и указание модели ссылки уже на неё. Альтернативно шлюз мог бы скачивать картинку с предоставленного URL, кодировать её в base64-формат и в таком виде передавать модели.

Довольно интересной особенностью форматов изображений является возможность [стеганографии](https://ru.wikipedia.org/wiki/%D0%A1%D1%82%D0%B5%D0%B3%D0%B0%D0%BD%D0%BE%D0%B3%D1%80%D0%B0%D1%84%D0%B8%D1%8F) - вшивания в изображение побочной информации так, чтобы визуально это не было заметно. Обычно такая информация вшивается как какая-нибудь мета-информация о картинке. В целом, никто не мешает в картинку вшить инструкции модели и посмотреть, реагирует ли она на них, тем самым выполнить jailbreak.

Удобным, но не критичным функционалом было бы преобразование нетекстовых форматов данных к текстовым. Например, [преобразование docx или pdf документов в текст](https://pandoc.org) с последующей передачей их в модель в рамках запроса.

### Поддержка протоколов взаимодействия AI-агентов друг с другом и с внешним миром

Есть два главных на данный момент протокола для взаимодействия AI-агентов друг с другом и с внешним миром: [MCP](https://modelcontextprotocol.io/docs/getting-started/intro) и [A2A](https://a2a-protocol.org/latest/).

Сначала про MCP. Это протокол взаимодействия модели с ресурсами (tool-ами), которыми могут быть базы данных, файловая система и т.п. Вообще говоря, что угодно можно обернуть в [MCP-интерфейс](https://modelcontextprotocol.io/docs/develop/build-server), снабдив каждый эндпоинт текстовым описанием, что он делает. Работает всё по уже привычным HTTP/SSE/JSON-RPC.

Казалось бы, не так сложно построить очередной прокси между [MCP Client и MCP Server](https://modelcontextprotocol.io/docs/learn/architecture). Но просто прокси не решает никаких проблем, а проблем много.

1. Все описания всех tool-ов всех подключённых MCP-серверов подгружаются в контекст каждого запроса к LLM. Так, большая часть контекста съедается именно повторяющимися описаниями tool-ов, и стоимость каждого запроса возрастает до неприличных размеров. Проблема решается на шлюзе за счёт введения Code Mode - режима, при котором модель вместо прямого последовательного вызова всех понадобившихся ей tool-ов из списка, напишет код (на Python, например), который вызовет только требуемые tool-ы как скрипт. В каждом запросе модель получает только короткий список мета-tool-ов (discover tools, read tool code, read tool docs, execute tool), с помощью которых модель сможет получить информацию о tool-ах и выбрать только те, что ей требуются. Такой подход может быть немного неочевидным, но по [заявлениям разработчиков Bifrost](https://docs.getbifrost.ai/mcp/code-mode) работает.
2. MCP - stateful протокол, поэтому на шлюзе придётся хранить распределённое состояние. Например, хранение идентификатора сессии в привязке к пользовательским учётным данным позволит не дать другому пользователю, узнавшему каким-то образом ID сессии, использовать эту сессию.
3. MCP требует реализации довольно нетривиальной логики по аутентификации клиентов с использованием OAuth 2.1. Более того, старые версии MCP серверов могут не поддерживать методов аутентификации, введённых в новых стандартах. Новый стандарт содержит отдельную секцию с требованиями к MCP Proxy, и список их [внушительный](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices).

A2A - протокол взаимодействия AI-агентов между собой. Поддерживается три транспорта: HTTP/SSE, HTTP/REST, gRPC. В состав протокола входят стриминговые взаимодействия и механизм уведомлений. Всё это агенты могут использовать для того, чтобы передавать информацию друг другу, в том числе о том, что для реализации некой задачи необходимо вызвать иной агент. Шлюз же должен решать задачи поиска агентов (discovery), роутинга между агентами и безопасности взаимодействий. Более полный список возможных фич можно посмотреть [тут](https://github.com/win4r/openclaw-a2a-gateway#key-features).
